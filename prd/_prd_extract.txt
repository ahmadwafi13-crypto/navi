1.3 Penggunaan WorkBuddy yang harus dapat dibuktikan

Untuk kompetisi, WorkBuddy harus menjadi lingkungan pembentukan/penjalanan workflow AI. Setiap peran
logis dikemas sebagai Skill/komponen yang dikenali WorkBuddy sesuai kemampuan akun, dan proses nyata
ditunjukkan melalui rekaman, jejak penggunaan tool, dan hasil ekspor. Jangan mengklaim bahwa aplikasi
web sendirian sudah memenuhi penggunaan WorkBuddy.

WorkBuddy Enterprise / Managed Agents dapat menjadi opsi hosting setelah kompetisi, tetapi API, lisensi,
harga, dan akses aktual perlu diverifikasi. Runtime web tidak boleh bergantung pada endpoint WorkBuddy
yang belum tersedia.

3. Skenario dan user journey

3.1 Alur utama: rapat menjadi tindakan

1. Pengguna memasukkan ringkasan rapat/chat, dilengkapi sumber opsional yang diizinkan.
2. Orchestrator membuat run ID dan memverifikasi identitas sesi; semua lampiran diberi label untrusted.
3. Interpreter menghasilkan kandidat tindakan email, calendar, task dalam skema terstruktur.
4. Conflict Detector membandingkan instruksi, kontak, tanggal, status final, dan perubahan kronologi.
5. Validator memeriksa aturan operasional, kewenangan, konten, prompt injection, dan kecocokan terhadap

     permintaan asli.
6. UI menanyakan hanya detail yang diperlukan; pertanyaan dapat dijawab per action.
7. Saat lengkap, UI menampilkan detail final per tindakan; masing-masing mempunyai action_id, version,

     risk, dan asal data.
8. Pengguna menolak, merevisi, atau menyetujui setiap tindakan secara eksplisit.
9. Gateway memverifikasi user, role, tenant, hash payload, versi, expiry, state, dan idempotency key.
10. Mock tool melakukan tindakan yang diizinkan dan mengembalikan receipt, bukan sekadar mengubah

     status UI.
11. UI menunjukkan hasil sukses/gagal/ditahan secara jujur; audit ditulis untuk seluruh transisi.

4.3 Prompt dan schema governance

 Setiap agent mempunyai system instruction versioned; perubahan prompt dibahas melalui pull request
     dan diuji otomatis.

 Structured output wajib tervalidasi JSON Schema/Zod; hasil tak valid tidak digunakan untuk aksi.
 Sumber dokumen disegel sebagai untrusted context; prompt injection detection merupakan pertahanan

     tambahan, bukan satu-satunya batas aman.
 Orchestrator membatasi putaran klarifikasi otomatis agar tidak looping. Untuk kasus yang belum

     terpecahkan, status ESCALATED dan manusia memutuskan.
 Log hanya menyimpan metadata dan cuplikan aman; raw transcript sensitif tidak diunggah ke repo

     publik.

6.1 Aturan approval paling penting

 Approval per action, bukan persetujuan global samar.
 Pengguna melihat field yang persis dieksekusi: recipient ID, address, subject, body, attachments, start/end

     time dan timezone.
 Payload diserialkan secara kanonis dan di-hash (mis. SHA-256); approval menyimpan plan_version,

     payload_hash, user_id, tenant_id, issued_at, expires_at.
 Saat gateway berjalan, ia menghitung ulang hash, memeriksa versi, memastikan actor berwenang, state

     valid, belum expired, belum digunakan, dan idempotency key unik.
 Jika ada satu field berubah, kembali ke AWAITING_APPROVAL versi baru.
 Seluruh aksi ditolak secara default jika approval tak ditemukan atau tidak cocok.
 Approval tindakan high-risk memerlukan konfirmasi tambahan; pembayaran riil di luar MVP.

7. UI/UX: pengalaman produk

7.1 Prinsip pengalaman

 Clarity before speed: status setiap tindakan mudah dibaca; tidak ada aksi yang disamarkan sebagai
     otomatis.

 Explain before approve: tampilkan alasan konflik, sumber, dan detail persis sebelum tombol persetujuan
     aktif.

 One decision at a time: klarifikasi relevan di dalam kartu action; tidak memaksa pengguna mengulang
     input.

 Safe defaults: tombol setujui disabled ketika field wajib kurang, akses tidak cukup, atau ada konflik kritis.
 Accessible by design: target WCAG 2.2 AA, seluruh kontrol keyboard-accessible, label eksplisit, fokus

     terlihat, screen-reader status, tanpa status yang hanya diwakili warna.

10.3 Pipeline GitHub Actions dan rilis

12. Feature branch -> pull request; CODEOWNERS untuk policy, prompts, gateway, dan workflow CI.
13. Job CI: lockfile install; lint/format; TypeScript typecheck; unit tests; schema tests; integration tests.
14. Job security: secret scan, dependency audit/SCA, SAST, permission policy diff; semua harus pass.
15. Job agent-eval: test dataset dan adversarial prompt injection; pastikan nol unauthorized execution.
16. Job web-e2e: Playwright desktop/mobile, approval flow, conflict states, accessibility checks.
17. Review manusia + branch protection; preview environment dibangun secara otomatis untuk inspeksi.
18. Release: staging / candidate -> smoke test -> persetujuan rilis -> production. Jangan melakukan DB

     migration destruktif dalam satu langkah otomatis.
19. Rollback: pin versi terakhir yang lulus; rollback UI/API, pertahankan audit; untuk perubahan schema

     gunakan expand/contract migration.

16.5 SSO, permission, dan keamanan integrasi

 Gunakan OIDC Authorization Code + PKCE atau sesi internal server yang tervalidasi; terbitkan token
     audience khusus NAVI. Jangan kirim token ERP jangka panjang ke frontend atau model.

 Konteks organisasi dihasilkan dari token yang terverifikasi: issuer, audience, expiration, tenant, user,
     scope, role, dan sesi; jangan percaya tenant_id dari browser.

 Konektor hanya memiliki least-privilege scopes, per-tenant isolation, rate limits, serta batas jumlah
     penerima. Klasifikasi informasi harus dicek sebelum membaca sumber.

 Approval hanya valid jika user berwenang, action version/hash cocok, token belum kedaluwarsa, dan
     rencana belum berubah. CSRF, replay protection, idempotency key, dan audit log wajib ada.

 Pada widget/iframe lintas origin, gunakan CSP frame-ancestors allowlist, postMessage dengan origin
     check, serta pembatasan cookie; prefer same-origin route jika memungkinkan.

 Untuk webhook, gunakan signature HMAC, timestamp tolerance, nonce/idempotency, dan rotasi rahasia;
     semua event eksternal diperlakukan sebagai data tanpa otoritas menyetujui tindakan.

 Untuk data riil, tetapkan retention, enkripsi at-rest/in-transit, lokasi penyimpanan, kebijakan logging dan
     pemrosesan data oleh provider sesuai persetujuan organisasi.

 Jika WorkBuddy Managed Agents belum tersedia untuk akun/region, gunakan WorkBuddy untuk
     workflow pengembangan dan demo, dengan mock adapter pada API platform. Jangan klaim akses API
     resmi yang belum diuji.

16.6 Pengembangan SDK, CI/CD, dan multi-tenant

 Workspace monorepo: apps/web (NAVI console), apps/api (approval + plan service), apps/worker
     (controlled execution), packages/sdk-js (widget/API client), packages/contracts (schemas),
     adapters/workbuddy, adapters/mock, adapters/org-app.

 Buat tenant-level connector config: OAuth scopes, allowed object types, branding, webhook URLs,
     notification channels, policy versions, retention; deny-by-default.

 GitHub Actions: lint + typecheck + unit + integration + policy/injection tests + browser E2E; wajib negatif
     tes unapproved execute sebelum bisa merge.

 Preview deploy setiap PR. Production release dari commit yang telah diperiksa, menjalankan migration
     yang kompatibel, staging smoke test, lalu promotion. Rollback tidak boleh mengubah bukti persetujuan.

 Metrik: plan_parse_accuracy, ambiguity_detection_rate, approval_bypass_count (target 0),
     execution_duplicate_count (target 0), p95 latency, audit_completeness, error rate.

 Integrasi organisasi baru diaktifkan bertahap: read-only pilot, mock execution, approval real + mock
     output, lalu real connector setelah izin dan pentest.

16.7 Ketersediaan WorkBuddy API dan status produk

Tencent Cloud memublikasikan WorkBuddy Managed Agents sebagai layanan enterprise yang mendukung
custom agents, APIs/SDKs, dan penyematan ke sistem OA atau aplikasi organisasi. Namun, fitur, harga, akses
kredensial, region, dan integrasinya harus diverifikasi di akun Tencent yang akan dipakai sebelum dinyatakan
production-ready. Sumber: https://indonesia.tencentcloud.com/products/workbuddy-managed-agents
Untuk penjurian, tetap tunjukkan penggunaan WorkBuddy yang benar-benar berjalan. Demo web atau mock
adapter tidak boleh diklaim telah terhubung ke runtime WorkBuddy apabila belum terverifikasi.

17. Identitas sementara NAVI dan tata kelola
merek

Untuk pengajuan hackathon, gunakan NAVI sebagai nama proyek / codename dan jangan menampilkan
kandidat nama komersial lain dalam materi publik. Judul yang konsisten: NAVI - Conflict-Aware Office Agent.
Blurb (9 kata): "Mengubah instruksi ambigu menjadi tindakan aman dengan persetujuan manusia."
NAVI hanya nama sementara dan bukan klaim kepemilikan merek. Perlu penelusuran resmi di PDKI,
terutama kelas 9 dan 42, termasuk ejaan dan pelafalan yang mirip. Tinjau status terkini, nomor permohonan,
pemilik, kelas, dan masa perlindungan. PDKI: https://pdki-indonesia.dgip.go.id/; klasifikasi:
https://skm.dgip.go.id/.
Proyek hackathon harus menggunakan data fiktif dan repo yang telah disanitasi. Nama rahasia, strategi
komersial, atau kode yang tidak diperlukan untuk bukti WorkBuddy sebaiknya tidak dimasukkan ke paket
submission; tetap penuhi seluruh dokumen wajib, sumber/workflow, serta evidence.
